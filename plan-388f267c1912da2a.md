# Pin-free parallel printer automation with durable production queues

Build one StationeersLua printer controller and a ScriptedScreens console, backed by a generated game/mod recipe catalog and compatible storage reservations, using two standard sorters and a shared flip-flop ingredient bus without printer-output valves or stackers.

## Summary

Implement a clean-design production service in `D:\StationeersLua` for the Autolathe, Hydraulic Pipe Bender, Electronics Printer, Rocket Manufactory, Tool Manufactory, and Security Printer. Discover machines by prefab hash, select the earliest eligible printer automatically, request ingredients from the existing storage controller, count production from native printer state, reuse useful leftovers, and return unused reagents to storage. Ingredient transfers are serialized; printing on different families is parallel.

This is a Lua program on an Integrated Circuit (Lua), not a vanilla IC10-only implementation. The console is a separate ScriptedScreens Lua chip. The deployment bundle embeds its recipe catalog, so no catalog-library chip, pin bindings, new runtime mod, or HTTP service is required.

## Confirmed requirements and boundaries

- One printer per family; all available upgrades are installed. Missing families should be reported as unavailable rather than preventing the remaining families from operating. Duplicate machines of one family are a topology error, not an implicit choice.
- Include all six families' recipes, including enabled-mod additions and tier-two recipes. Never include the advanced packaging machine, automated oven, or other production families.
- No d0–d5 assignments or pin-based reads. Discover by prefab/name hashes and use discovered reference IDs for individual logic, slot, and memory operations.
- A screen supports item and quantity selection; a versioned production API supports programmatic requests.
- Programmatic requests default to strict, full-resource reservation: insufficient resources return an error before production or ingredient movement. The console explicitly requests partial-and-wait behavior: produce the feasible quantity, persist the remainder, and resume after restocking.
- Keep every unfinished accepted request durable until it completes or is explicitly cancelled. Completed/cancelled history may be bounded; live work may never be evicted to admit new work.
- Finished products go to a shared passive collection point. Unused reagents go to the existing storage input.
- Retain reagent types needed by the next runnable task on that same printer; purge types that are not useful and purge all remaining contents when no runnable work remains.
- Include pause/resume, safe cancellation, retry, maintenance mode, shortage diagnostics, and request idempotency.
- Use the shared ingredient bus with low-power digital flip-flop branches. No printer-output stacker or valve; output classification may use a standard sorter, but production counts must not depend on it.
- The storage outlet has a user-provided manual splitter, normally pointed at the printers. **No automated outlet splitter and no routing chip are in scope.** Prepare an explicit delivery handoff interface for a later routing chip without implementing it now.
- Compatible storage-controller additions are allowed. Preserve the current uncommitted drain/routing fixes and all unrelated changes. Do not edit workshop content, game data, mod settings, or unrelated scripts. Do not add/remove explanatory code comments; keep existing comments.

### Printer state and pin-free ingredient accounting

- Relevant printer properties include `RecipeHash`, `Reagents`, `Activate`, `On`, `Open`, `Lock`, `CompletionRatio`, `ImportCount`, and `ExportCount`, plus native printer memory.
- The shipped `Assets\LuaLibrary\stationeers-ic.lua` describes `ic.read_reagent` and `ic.rmap` as pin-based (lines 75–87). The guides do not document reference-ID equivalents. Avoid these APIs entirely in this design; do not guess that passing a prefab hash or reference ID to them works.
- Maintain a persistent per-reagent ledger for each owned printer. Establish an empty baseline on first adoption; credit only known stacks released from the held ingress sorter and confirmed by `ImportCount` and total `Reagents` while the target printer is not consuming ingredients. Debit using the catalog recipe after confirmed native production. Validate total mass against `Reagents` at quiescent boundaries.
- Total `Reagents` does not independently prove reagent composition. Correctness depends on exclusive ownership, known input stacks, a verified catalog, and a clean or reconciled baseline. Unexpected state must block/reconcile rather than be guessed away.
- `ExportCount` counts exported stacks, including expelled ingots. Separate printing and purging phases; never count every export as a finished product.
- Community internal-memory documentation describes addresses 0–53 as programmable, 54–62 as missing-reagent diagnostics, and 63 as the stack pointer. `ExecuteRecipe` is opcode 2 with an 8-bit quantity at bits 8–15 and an item hash at bits 16–47; `WaitUntilNextValid` is 3, `JumpToAddress` is 5, `EjectReagent` is 7, and `EjectAllReagents` is 8. Confirm these against the installed game during commissioning before using them for movement.
- Missing-reagent quantities are byte-limited, rounded, and have historically had incorrect batch calculations. Use their reagent identities diagnostically only, never as the resource-reservation source of truth.
- Selective ejection expels an entire reagent type, not an arbitrary surplus quantity. The reuse policy therefore retains useful types between immediately runnable tasks, possibly including their unavoidable small rounded-transfer surplus. It does not promise exact partial-type trimming.

## Physical topology

### Ingredient path

```text
Existing storage request outlet
  -> user-managed MANUAL splitter, normally pointed to printers
  -> Printers.Ingress (STANDARD sorter, Logic mode)
       return output -> storage input before Storage.InputValve
       feed output   -> shared ingredient bus
                          -> Printers.Feed.Autolathe
                          -> Printers.Feed.PipeBender
                          -> Printers.Feed.Electronics
                          -> Printers.Feed.Rocket
                          -> Printers.Feed.Tool
                          -> Printers.Feed.Security
                          -> terminal safe return to storage input
```

Each feed device is a digital flip-flop splitter. Its side branch leads directly to the corresponding printer input; its through branch leads to the next bus splitter. During a transfer, all preceding branches pass through and exactly the selected branch diverts. Enable the required path before release, verify settings by read-back, and retain that route until the target's exact import is confirmed. Never change branches merely because a transient chute slot looks empty.

### Output path

```text
All six printer outputs, merged passively
  -> Printers.OutputClassifier (STANDARD sorter, Logic mode)
       known ingot prefab -> storage input before Storage.InputValve
       catalog product    -> shared passive product collection
       unknown prefab     -> HOLD, expose diagnostic
```

The two sorters use `Mode = 2` and one-shot `Output = -1` at rest. In this mode the sorter holds its input until explicitly directed and automatically resets Output after release. Verify physical port orientation once; standard sorter Output values must not be confused with digital splitter Mode values.

No new output valve, stacker, refrigerated vending machine, proximity sensor, or per-printer output counter is required. All six printers are productive machines; Security is not an ingredient buffer.

Use exact device names above for routing-device grouping; printer discovery itself is by the six supported prefab hashes. Printer/controller/console and storage API endpoints must share a reachable StationeersLua data network. Do not assume arbitrary data bridges also bridge Lua RPC.

### Hardware/power comparison

- Recommended: two standard sorters and six digital feed splitters, plus the user's manual outlet selector. Published nominal routing power is 2 × 5 W + 6 × 10 W = 70 W if every added powered routing device is on; this excludes chips, screen, printers, and existing storage hardware. Treat this as a device-budget estimate, not a measured guarantee.
- Independent per-printer feeders add held-item routing hardware and more control state; useful for concurrent ingestion, but not necessary for concurrent printing.
- The workshop's all-ingots-in-one-printer scheme is smaller logically but serializes printer ownership and does not satisfy this production API.
- Begin with the two sorters powered while service is enabled. Turn idle printers off after outputs/cleanup settle. Gate unused bus paths only when no transfer can be in flight; do not chase a few watts by cutting power mid-transfer. Measure actual idle and mixed-job behavior during commissioning.

### Production request

Use `api_version = 1` and the `printers.*` method namespace. A request includes:
- `client_request_id`: bounded string, unique within stable sender identity.
- `prefab_hash`: canonical signed 32-bit item hash.
- `quantity`: finite positive integer; initial maximum 1,000,000, additionally limited by exact-integer arithmetic bounds.
- optional `preferred_family`: override only if that family has an eligible recipe.

`printers.request` is strict. `printers.request_partial` is the console's explicitly partial-and-wait submission. Both use the same scheduler and durable task records; the endpoint distinction makes shortage behavior unambiguous.

Strict insufficient-resource response:

```text
{api_version=1, ok=false, code="insufficient_resources",
 shortfalls=[{prefab_hash, required_quantity, available_quantity, missing_quantity}],
 feasible_quantity=<advisory count>}
```

No task is accepted and no ingredients move on a clean strict rejection. Stock changes or physical faults after acceptance are asynchronous task failures/blocks, not retroactively described as clean rejection.

Accepted response contains request ID, selected family, policy, state, requested count, completed count, and current shortfalls. Partial requests retain the full requested count even if feasible_quantity is zero. Their shortage is a status/error field, not an ambiguous `ok=false` response to an accepted task.

Other methods:
- `printers.list_recipes`: stable paginated/searchable/filterable results with catalog revision and unavailable reasons.
- `printers.quote`: advisory cost, candidates, feasible count, and shortfalls; not a reservation.
- `printers.request_status`, `printers.list_requests`, `printers.get_state`.
- `printers.pause`, `printers.resume`, `printers.cancel`, `printers.retry`.
- `printers.maintenance`: explicit quiesce/release/re-adopt operation; cannot erase a blocked request or overwrite an unrelated active native program.

Publish revisioned task/state events under `printers/v1/...`; treat RPC queries as authoritative. Return copied response tables so callers cannot mutate live records. Bound page size, string length, task count, payload size, and finite numeric validation. Idempotent retries with the same ID but different contents return `idempotency_conflict`.

### Task and printer state

Task states: `reserving`, `queued`, `feeding`, `printing`, `waiting_resources`, `paused`, `cleaning`, `completed`, `cancel_pending`, `cancelled`, and `blocked` with structured fault information. Persist requested/completed/remaining counts, family and recipe identity, policy, reservation references, input ledger credits, operation sequence, and last error.

Per-printer record: discovered reference ID and prefab hash, owned/native-program fingerprint, last import/export counts, per-resource contents and allocations, active request, current single-item native command, feed receipt state, purge state, and maintenance status.

Global record: schema, persistent controller identity and request sequence, task order/idempotency index, catalog revision, output-ownership token, one ingredient transfer journal, and global output-classifier release state.

## Scheduling and resource mathematics

- One cooperative main scheduler is the only actuator owner and state writer. Network/UI handlers enqueue bounded commands; yielded RPC handlers may wait for reservation results without freezing the main device loop. Verify the actual handler parameter order against the installed runtime: shipped guide and reference stubs disagree, while the existing storage code uses `(payload, sender)`.
- Each tick services output classification, confirms in-flight movement, advances each of six printer state machines by bounded work, and advances the single feed transfer. Cache discovery and catalog indexes; do not scan every device or recipe every tick.
- FIFO inside a family, skipping paused/shortage-blocked tasks so one unavailable recipe does not block all useful work. Round-robin feed opportunities across runnable families prevent a large job monopolizing the ingredient bus.
- Automatic assignment filters capable/present families first, then chooses the shortest estimated finish time including queued work, then estimated energy, then deterministic family order. Time/energy are estimates based on XML and the installed upgrade assumption; do not present them as measured completion guarantees. Reconsider an unassigned partial job before its first successful reservation; freeze the chosen family once resources are reserved or delivered.
- Maintain exact fixed-point consumption and ledger quantities. For resource r, deficit for n items is `max(0, cost[r] * n - unallocated_local_credit[r])`.
- Storage requests remain integer item quantities: request `ceil(deficit / reagent_units_per_ingot_item)` for each resource, rounding the aggregate deficit once, not each product separately.
- Obtain feasible count from the minimum resource bound over the complete recipe vector after existing allocations/reservations. Query results are advisory; atomically reserve the entire vector before committing a production slice. If the snapshot raced, recompute/retry without moving materials.
- Strict tasks reserve the full procurement vector at acceptance. Deliver it in bounded slices as needed; do not dump a million-item job's ingredients into a printer all at once.
- Partial tasks reserve the maximum currently feasible bounded slice, print it, and then repeat. If zero is feasible, persist `waiting_resources`, expose shortages, release useless allocations, clean the printer, and try another task/family. Retry on inventory revisions plus a bounded periodic fallback because existing storage intake does not currently publish every inventory revision.
- Never count ingredients in transit or merely reserved in storage as usable printer contents. Never spend retained local credit twice. Unissued reserved ingredients are cancellable; released physical ingredients are not rollbackable.

## Native production, pause, and cancellation

Use **one item per native command in the first implementation**. This settles cancellation semantics without assuming that rewriting memory changes a cached, already executing multi-item command. It also naturally supports request quantities above 255 without byte overflow. Parallelism is between printers, not by allowing unbounded native queues.

1. At a quiescent printer boundary, confirm no unrelated program/recipe change, no purge, and no occupied product-export slot.
2. Persist a `prepared` record with task ID, recipe fingerprint, quantity 1, export baseline, resource ledger baseline, and the exact expected program words.
3. Stop/park the owned printer while installing the program. Clear/write only addresses 0–53; never write missing-reagent slots or pointer slot 63.
4. Install Wait/Execute(1), a harmless jump loop after the command, and an entry jump at address 53 so the existing native pointer can reach the new command without writing the pointer. Native Execute(1) becomes zero after export, so looping cannot reproduce it. Validate entry/wait/execute behavior during commissioning.
5. Read back the program, persist `armed`, then enable the printer. Do not enable production if persistence or read-back failed.
6. Confirm one completed product from coherent native remaining quantity/cleared command, export-counter delta, activation state, and the no-purge phase. Check the recipe and reconcile post-completion reagent mass. Persist progress before issuing the next command.
7. `CompletionRatio` is UI progress only, never a finished-item counter. Output blockage leaves the task running/blocked, not completed.

Pause stops issuing another single-item command and lets the current item finish. Cancellation similarly finishes at most the already armed item, stops future commands, releases unissued reservations, and performs leftover cleanup. A task paused or cancelled before arming produces nothing. A controller fault may power the affected printer off mid-item; recovery preserves the armed record and resolves it before any retry.

The single-item strategy adds native/controller handoff latency to very fast recipes. Measure it with actual upgraded printers. Larger bounded chunks are a later optimization only after safe in-progress quantity reduction/cancellation is proven; do not silently change cancellation to 'finish 255 more items'.

## Ingredient delivery and storage-controller additions

Keep the existing storage API version-1 methods and response shapes available. Add capability fields to `storage.get_config` and additive methods:

- `storage.output_acquire` / `storage.output_release`: persistent, owner-checked exclusive use of the shared request outlet for this controller. Acquiring waits for existing work to settle and refuses an ambiguous pre-existing transfer. New unrelated output requests return `output_busy` while printer mode owns the line; already queued legacy requests are held, not dropped. Input storage remains operational.
- `storage.reserve_batch`: idempotently reserve an explicit vector `{prefab_hash, quantity}` atomically across groups. All resources are validated before any reservation changes. On shortage return all shortfalls and reserve nothing. Store batch ID, owner, recipe/client correlation, resource allocations, and cumulative dispatched/remaining quantities.
- `storage.batch_status`: recover pending reservation and transfer outcomes by stable ID after timeout/restart.
- `storage.dispatch_reserved`: carve a bounded one-resource delivery from a batch without double-reserving it; issue one tracked delivery at a time on the existing exact-quantity output machinery. Include delivery ID, resource, exact quantity, and intended printer-family metadata. This metadata does not actuate the user's manual outlet splitter.
- `storage.delivery_ack`: idempotently acknowledge the downstream printer's verified receipt. Preserve the delivery handoff until acknowledged; 'released from storage' is not 'received by printer'.
- `storage.release_batch`: release only undelivered/unissued allocations. Never claim that cancellation recovered material already exported.

The future routing chip can insert a readiness/handoff stage around `dispatch_reserved`/`delivery_ack`. No future router is required or implemented for this build.

Feed procedure:
1. Establish exclusive outlet ownership, ensure no older unknown stack is entering the ingredient path, and persist the intended delivery before asking storage to dispatch.
2. Wait for the held ingress item. Check exact prefab and quantity against the outstanding manifest; a delivery larger than one physical stack remains the same manifest with cumulative receipts.
3. Park the target printer so no ingredient consumption can occur; other printers continue printing.
4. Persist the per-stack receipt baseline, configure/read back the bus route, and release exactly that held stack using the ingress sorter's one-shot Output.
5. Wait for import-counter change and the expected total-Reagents increase at that printer, with expected mass including the generated ingot conversion. Only then credit its per-resource ledger, checkpoint, and permit another bus route.
6. Acknowledge the manifest only when its entire quantity is confirmed. Duplicate callbacks, retries, and acknowledgements must not request or credit another copy.
7. On mismatch/timeout, stop dispatch and hold unknown input; retain the reservation/transfer journal for recovery. Never send a stack to a printer merely because its hash matches something that printer might need.

In default printer mode the shared outlet is dedicated to the automation service. To use the existing storage console for manual deliveries: quiesce printers, settle transfers, explicitly release software outlet ownership, then manually move the user's splitter. Reverse this procedure before restarting automation. The software neither moves nor assumes it can read that manual splitter.

## Leftover handling and output classification

- Printing and ejection cannot run simultaneously on the same printer. Other printers may print while one cleans up.
- After an item/slice/task, examine the next runnable same-printer task. Transfer only legitimately unallocated local reagent credit to it, releasing any corresponding storage reservation before reuse; never credit both local contents and undelivered stock for the same consumption.
- Run native EjectReagent for types unused by that task; its whole-type limitation is explicit. If no immediately runnable task exists, EjectAllReagents establishes an empty baseline. Waiting-for-stock or paused work must not hoard otherwise unused ingredients indefinitely.
- Prepare a durable purge record before enabling ejection. Verify command retirement and post-purge total mass at an idle boundary. Expected ingot hashes route back to storage; catalog product hashes route to collection; unknown output remains held for diagnosis.
- Do not increment product counts during any purge. Keep export-counter baselines separate between production and cleanup.
- A product is considered produced when the native state proves it was exported by the printer, not when a player collects it. Cleanup completion means surplus has left the printer and been safely handed to the configured return path; do not falsely report that a passive downstream chute's entire contents have already been credited in storage. Commissioning must verify real storage intake and backpressure.
- Drain output/backpressure before switching recipes or powering a printer off. Unused resources must have a return path even if product collection is full; diagnose which branch is blocked.

## Durable persistence and recovery

Installed limits are 8,192 characters per value and 32,768 total per chip; init/tick budgets are 500,000/50,000 instructions. **Do not raise these settings.** Do not persist the whole catalog with each tick.

Use compact, sharded A/B checkpoints in each controller:
- At most three chunks of up to 4,096 ASCII characters for one checkpoint, with total encoded body capped at 12,000 characters.
- Write inactive-generation chunks and length/schema/revision metadata, read back each write, then commit a small active-generation marker last. Keep the previous committed generation intact while staging the new one. Include key/metadata overhead in the total limit.
- Use numeric hashes/bounded ASCII internal IDs in the durable control record; UI Unicode preferences can use separate bounded storage. This makes byte/character capacity checks predictable.
- Initial count limits: at most 24 unfinished production requests and 16 recent terminal records, but the encoded-size limit may reject earlier. Trim terminal history first. Reject new work before state mutation if its durable representation cannot fit.
- Check every `ic.persist.set` result and read-back. False returns are failures, not successful acceptance. Persistence failure stops new actuation; report `persistence_error`/`persistence_full`.
- Snapshot acceptance intent before calling storage. If the reservation reply is lost, retry/query the same stable client key. A task is acknowledged accepted only after both its reservation outcome and its local record are durable.
- Store operation intent before every irreversible release/native start and confirmed outcome before subsequent dependent work.
- On startup, discover and park owned machines without clearing counters/programs first. Restore the committed journal, query storage for outstanding batch/delivery IDs, and reconcile native memory/import/export/mass observations.
- Do not replace a durable armed Execute command after a restart merely because the UI lost its response. A completed single-item command can advance the task once; a still-live one resumes once. Counter rollback, recipe changes, missing devices, catalog mismatch, foreign memory, and irreconcilable in-flight movement block affected work.
- Invalid committed data must not silently fall back to an older action ledger and resume physical work. Use older data for diagnostics only until reconciliation establishes safety.
- First adoption of an idle printer with unknown contents requires explicit commissioning/adoption approval; purge it to storage and establish zero. An unrelated active job is not overwritten or adopted silently.
- Persistence covers save/load and same-source power/pull cycles as documented by the mod. Code replacement and unsaved-world rollback need explicit upgrade/reconciliation checks, not unconditional exactly-once promises.

## Risks and considerations

1. **No confirmed runtime recipe enumeration.** The generated catalog is the chosen implementation. XML source/load-order changes require refresh; C#-only recipe patches need an explicit future export/integration, not invented hashes.
2. **Pin-free composition accounting is derived.** Total Reagents verifies mass, not composition; exclusive ownership and a known baseline are mandatory. Missing-reagent byte quantities are not a substitute.
3. **Native-memory and fractional behavior need actual game checks.** Research documentation is not physical commissioning. Do not activate an unverified memory program or claim fractional returns work from mocked tests alone.
4. **One-item commands trade throughput for reliable control.** Their overhead may matter for sub-second upgraded recipes. Parallel printers still work; only a separately proven optimization may increase chunks later.
5. **Manual outlet selection imposes exclusivity.** The current storage line cannot physically honor arbitrary destinations. Other output clients must wait/use maintenance while the printer path owns it. The future routing chip remains out of scope.
6. **Durable storage integration is real scope, not an adapter shortcut.** Multi-resource atomic reservations and restart-safe handoffs cannot be guaranteed by a client that merely issues the current one-resource API repeatedly.
7. **Persistent capacity is finite.** Every live request remains stored, but new requests can be rejected when space is exhausted. Never increase mod limits or trim unfinished work as a workaround.
8. **Physical delivery is irreversible.** After material leaves storage, errors are blocked/faulted transactions requiring reconciliation, not clean rollback. Power/controller loss can leave the currently armed native item running, which recovery must count once.
9. **Downstream collection is passive.** The service proves production at the printer and safe routing handoff, not that a player collected it or every downstream chute has emptied.
10. **Protect existing local changes.** Storage already has uncommitted drain fixes and tests. Extend their behavior carefully, avoid unrelated cleanup, and review the complete working-tree delta before any commit/export.
